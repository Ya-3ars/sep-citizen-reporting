System Architecture
SOLID Principles — Architecture Review · how our Spring Boot layered backend applies each principle

SOLID is a set of five object-oriented design principles that keep code maintainable and extensible. Our backend follows the classic layered structure Controller → Service → Repository → JPA Entity, which naturally supports all five. Each principle below lists how we comply and what a violation would look like.

S Single Responsibility Principle A class should have one reason to change.
✓ We comply: ReportController only handles HTTP, ReportService holds business logic, ReportRepository only does persistence. Photo handling lives in its own PhotoService.
✗ Violation: a single ReportManager class that parses the HTTP request, validates, writes to the DB, and resizes the uploaded photo — four reasons to change in one place.
O Open/Closed Principle Open for extension, closed for modification.
✓ We comply: report categories (pothole, pollution, parking) are an enum / lookup, so adding a new category needs no change to the service or controller logic. New validation rules can be added as separate Validator beans.
✗ Violation: a big if (type.equals("pothole")) … else if … chain in the service that must be edited every time a new report type is introduced.
L Liskov Substitution Principle Subtypes must be usable in place of their base type.
✓ We comply: any JpaRepository<Report, Long> implementation Spring injects behaves identically to the interface contract — the service never needs to know which concrete implementation it got.
✗ Violation: a ReadOnlyReportRepository that extends the repository interface but throws on save() — callers expecting a working save() would break.
I Interface Segregation Principle Don't force clients to depend on methods they don't use.
✓ We comply: separate focused interfaces — ReportRepository, PhotoRepository, UserRepository — so the Android citizen endpoints never see staff-only operations.
✗ Violation: one fat DataService interface with saveReport(), deleteUser(), resizePhoto(), exportCsv() that every consumer must implement or depend on.
D Dependency Inversion Principle Depend on abstractions, not concretions.
✓ We comply: ReportService depends on the ReportRepository interface, injected by Spring's IoC container — not on a hand-built PostgreSQL class. Swapping the DB or mocking it in tests needs no service change.
✗ Violation: ReportService doing new PostgresConnection() directly in its constructor, hard-wiring the high-level logic to a low-level detail.
Backend Class Layers · the classes referenced in the SOLID review, by layer

Each layer depends only on the layer below it, through interfaces (Dependency Inversion). Photo has no own controller — photos only exist attached to a report, so they are served via /reports/{id}/photo sub-routes (YAGNI: a standalone PhotoController would expose routes nobody calls).

API Contract · the HTTP endpoints both frontends call — the agreed seam between backend and clients
Base path All endpoints are under /api. Example: /api/reports.
Format JSON request & response bodies (Content-Type: application/json), except photo upload which is multipart/form-data.
Auth Staff endpoints require a JWT sent as Authorization: Bearer <token>. Public endpoints need no token. (JWT chosen over cookies so Android and web authenticate identically.)
Errors Non-2xx responses return { "timestamp", "status", "error", "message" }. Validation failures = 400, missing token = 401, wrong role = 403, unknown id = 404.

GET/api/reports staff — (query: ?status=&category=&page=) 200 OK + paginated list Staff dashboard loads reports, optionally filtered by status/category.

Authentication
MethodPathAuthRequest bodySuccessWhat it does
POST/api/auth/login public { username, password } 200 OK + { token, role } Staff logs in. Returns a JWT the client sends on every later staff call.

Public vs staff mirrors the two frontends: the Android app only ever calls the three public endpoints (submit report, attach photo, view photo). Every staff endpoint — list, edit, delete — is the web dashboard, gated behind login. This is the contract Yoana (Android) and Charlene (Web) build against while the backend is implemented in parallel.

Relationships & integrity rules
  • user 1 — 0..* report via report.updated_by (who last edited). A staff member edits many reports; a report has at most one last-editor.
  • report 1 — 0..* photo via photo.report_id. Deleting a report cascades to delete its photos.
  • No citizen table: reports are anonymous, so there is no created_by link.
  • Deleting a user sets report.updated_by to NULL (reports are preserved, edit attribution is cleared).
Alternatives We Considered & Why We Rejected Them · the decision record behind choosing Hybrid

Before settling on the Hybrid design, we evaluated three single-platform options against the assignment's core needs: citizens reporting in the field (needing camera + GPS), staff managing reports on a desk setup, and one shared data store. Each alternative failed on at least one of these. This record is kept for the written report.

🌐 Web Application (browser app for both roles) Rejected
In its favour
  • One codebase, both roles
  • Leaflet.js + OSM work natively
  • No install — citizens open a URL
  • Easiest to demo (localhost)
Against
  • No native camera/GPS in a desktop browser
  • Mobile photo capture needs WebView hacks
  • Weakest fit for field reporting
Dealbreaker: citizens report defects outdoors, on their phones — a browser can't reliably reach the camera and GPS the way a native app can. The core citizen use-case is compromised.
🖥 Desktop Application (JavaFX, installed per machine) Rejected
In its favour
  • Pure Java — closest to team's known skills
  • Possible to avoid JavaScript entirely
Against
  • Citizens won't install a desktop app
  • Map integration hardest of all options
  • Standalone → no shared data between users
  • Fragile WebView JS↔Java bridge; JRE packaging pain
Dealbreaker: a desktop install is a non-starter for citizens reporting on the move, and a standalone app can't give staff a shared, always-current view of all reports.
📱 Mobile-only (one Android app for citizens AND staff) Rejected
In its favour
  • Native GPS + camera for citizens
  • Most realistic for the citizen side
  • High visual impact in a demo
Against
  • Staff managing reports on a phone is poor UX
  • A separate staff UI becomes a second project anyway
  • Steepest learning curve; Android lifecycle complexity
Dealbreaker: staff need a wide-screen dashboard to triage, edit and delete reports — cramming that into a phone app is painful, and building a second staff UI defeats the "single platform" simplicity that made mobile-only attractive.
🏛 Hybrid (Android citizens + Web staff + shared backend) Chosen
Hybrid is the only option that serves both actors on the device that fits them: a native Android app gives citizens real camera + GPS in the field, while a web dashboard gives staff a proper wide-screen management view — both backed by one shared Spring Boot + PostgreSQL backend, so all data is consistent and live. The cost we accepted: it is the most work (two frontends) and requires both Java and JavaScript. We judged that trade-off worthwhile because it's the only design with no compromise on either core use-case.

Process Model · how we run the project — and why

We use a Kanban process: work is visualised on a board (To Do → In Progress → Done), pulled when a member has capacity, with work-in-progress (WIP) limits to keep focus and surface bottlenecks. The board is organised into milestone phases that align with the course's interim-review deadlines.

Kanban practices we follow
  • Visualise all work on the board
  • WIP limit: max 2 cards In Progress per person
  • Pull-based: take the next card when free
  • Weekly team sync + a shared group chat for blockers
Why Kanban, not pure Scrum

Pure Scrum assumes a dedicated, full-time team with a real Product Owner and daily standups. As five part-time students with no external customer and fixed external deadlines, that ceremony overhead didn't fit. Kanban's lighter, flow-based approach does — we keep a backlog, defined roles, and a board, but replace daily standups with a weekly sync and manage flow with WIP limits rather than fixed sprint commitments.
